# 语音电话功能实现计划

## 背景发现

经过深入探索，发现**项目已存在完整的语音电话基础设施骨架**：proto 协议（VoiceCallRequest/Response）、Rust 双向通信（io_loop.rs 的 start_voice_call / connection.rs 的 handle_voice_call）、Android 原生录音（AudioRecordHandle.kt）、Flutter 事件流（on_voice_call_waiting/started/closed）、桌面端 UI（_VoiceCallMenu + voiceCall() 菜单项）。

但存在两个致命断裂：
1. **Android 端 Opus 是 stub 空实现**——`encode_vec_float` 返回假包 `0xF8 0xFF`，`decode_float` 返回 `Unimplemented`，移动端完全无法编解码音频
2. **移动端播放端不支持实时 PCM 流**——audioplayers 只能播放完整 WAV 文件，不能持续喂 PCM 帧

此外还缺少：连接质量预检测、通话中网络质量监控与降级、移动端顶部直接入口。

## 实现方案

### 第一阶段：移动端 Opus 编解码（Dart 层）

**新增依赖**（pubspec.yaml）：
- `opus_dart: ^3.0.1` — Opus 编解码 Dart 绑定
- `opus_flutter: ^3.0.3` — 跨平台 libopus 原生库
- `flutter_sound: ^9.10.0` — PCM 流实时播放（audioplayers 不支持）

**新建文件 `flutter/lib/common/voice_call_codec.dart`**：
- `VoiceCallCodec` 类，封装 opus_dart 的 `SimpleOpusEncoder` 和 `SimpleOpusDecoder`
- 采样率 48000、单声道（VoIP 用单声道更省带宽）、Application.voip
- `encode(Float32List pcm) → Uint8List` — 编码 PCM 到 Opus
- `decode(Uint8List opus) → Float32List` — 解码 Opus 到 PCM
- `dispose()` — 释放原生资源

**新建文件 `flutter/lib/common/voice_call_audio.dart`**：
- `VoiceCallAudio` 类，管理移动端音频采集和播放
- 采集：`record.startStream(RecordConfig(encoder: pcm16bits, sampleRate: 48000, numChannels: 1, autoGain: true, echoCancel: true, noiseSuppress: true))` → Int16 流 → 转 Float32List → `VoiceCallCodec.encode()` → 通过新增 FFI 方法传回 Rust
- 播放：Rust 通过 FFI 事件流推送 Opus bytes → `VoiceCallCodec.decode()` → Float32List → `flutter_sound.feedFromStream()` 实时播放
- 格式统一：全链路使用 Float32（record 输出 Int16，转 Float32 后送 Opus 编码器；解码出 Float32 直接喂 flutter_sound）

### 第二阶段：FFI 桥接（Dart↔Rust 传输层）

**新增 Rust FFI 函数**（flutter_ffi.rs + bridge_generated.rs + bridge_generated.io.rs + generated_bridge.dart）：
- `session_send_voice_call_audio(session_id, opus_data: Vec<u8>)` — Dart 编码后的 Opus bytes 传回 Rust，Rust 装入 `AudioFrame{data: opus_bytes}` 发给对端
- 复用现有的 `AudioFrame` proto 消息（字段 11），不新增 proto 字段

**新增 Rust→Dart 事件推送**（flutter.rs）：
- 在 `io_loop.rs` 的 AudioFrame 处理中，当处于语音通话模式时，将 Opus bytes 通过 `push_event` 推给 Flutter（事件名 `voice_call_audio_frame`，字段 `data` 为 base64 编码的 Opus bytes）
- 仅移动端走此路径（桌面端仍在 Rust 内用 cpal 播放）

### 第三阶段：连接质量检测与降级

**新建文件 `flutter/lib/common/voice_call_quality.dart`**：
- `VoiceCallQuality` 类，负责通话前检测和通话中监控
- **通话前检测**：复用 `QualityMonitorModel` 的 delay 和 speed 数据（来自 TestDelay 机制）
  - 延迟 < 200ms 且速度 > 5kB/s → 绿灯，建议通话
  - 延迟 200-400ms 或速度 2-5kB/s → 黄灯，提示"网络一般，通话可能不流畅"
  - 延迟 > 400ms 或速度 < 2kB/s → 红灯，提示"网络较差，不建议语音通话"
- **通话中监控**：每 3 秒采样一次 delay
  - 延迟 > 300ms → 降低 Opus 码率（从默认 24kbps 降到 16kbps，通过重建编码器）
  - 延迟 > 500ms → 进一步降到 8kbps，UI 提示"网络较差"
  - 延迟 > 800ms 或连续丢包 → 提示"网络极差，建议挂断"
  - 延迟恢复正常 → 自动提升码率
- **码率动态调整**：销毁旧编码器，用新 `bitrate` 参数创建 `SimpleOpusEncoder`，通过 FFI 通知对端也调整解码器

### 第四阶段：移动端 UI

**修改 `flutter/lib/mobile/pages/remote_page.dart`**：

## 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 移动端 Opus | opus_dart + opus_flutter | 用户选择，纯 Flutter 方案最灵活 |
| 移动端采集 | record 包 startStream | 已有依赖，支持 PCM 流 + 回声消除 |
| 移动端播放 | flutter_sound | 唯一支持实时 PCM 流播放的 Flutter 包 |
| 传输 | 复用 AudioFrame proto | 不新增 proto 字段，与桌面端兼容 |
| 质量检测 | 复用 TestDelay 机制 | 已有 1 秒/次延迟测量，无需新建协议 |
| 码率降级 | 重建编码器 | opus_dart 不支持运行时改码率，需重建 |
| 单声道 | 48kHz mono | VoIP 标准配置，省一半带宽 |
| 桌面端改动 | 最小化 | 桌面端已有完整 Rust Opus 链路，只补 UI 和质量检测 |

## 兼容性

- **桌面端 PC↔PC**：不受影响，继续使用 Rust cpal + magnum_opus 链路
- **移动端 → PC**：移动端用 Dart Opus 编解码，PC 端用 Rust Opus，两端都生成标准 Opus 包，互通无问题
- **移动端 → 移动端**：两端都用 Dart Opus，标准 Opus 格式互通
- **Proto 协议**：不新增字段，复用 AudioFrame，与旧版本兼容
