# LUODA v3.0.1 全量测试 + 优化 + CI 最终构建计划

## 总体流程
本地 10 轮全量测试（含 OPPO 真机 ↔ PC 双端 E2E）→ 修复发现的问题与资源浪费 → 提交推送到 origin/3.1.1 触发 CI → 全程监控 CI 报错并即时修复 → 产出最终版本。

**工具路径**：
- Flutter: `J:/codex-work/flutter-sdk/flutter/bin/flutter.bat`
- adb: `J:/codex-work/.toolchains/android-sdk/platform-tools/adb.exe`
- 真机: OPPO PFUM10 (7358bbbb)

---

## Phase 0: 环境准备（~15分钟）
1. 运行 `flutter/kill_luoda.ps1` 结束 4 个运行中的 luoda.exe 进程
2. 探测可用的 vcpkg 构建环境（C:/vcpkg 或 D:/vcpkg，8/22 凌晨有过成功构建记录，从构建指纹反查当时的环境变量）
3. 检查手机上已安装的 LDesk 应用版本（`adb shell pm list packages | grep luoda`）
4. 清理调试残留：`preview_b64.html`、`preview_ref.html`、`preview_ref.png`（不入库）；核对 `proguard-rules` 与 `proguard-rules.pro` 重复问题（Gradle 默认认 `.pro` 后缀）

## Phase 1: 静态验证 — 测试第 1 轮（~15分钟）
1. `flutter analyze` 全量分析——确认本次修改（file_viewer/chat_model/desktop_home_page/main.cpp）无新增 error；顺带记录 81 个预存 warning 中与改动文件相关的
2. Rust 修改的编译验证（依赖 Phase 0 找到的 vcpkg 环境）
3. 确认 FFI bridge 无需重新生成（flutter_ffi.rs 未改动）

## Phase 2: 重建 PC 端（~40分钟，后台执行）
1. `cargo build --release --features flutter`——同时产出 service/naming 二进制，验证上次的 `windows_subsystem="windows"` 修改可编译
2. PowerShell 读取 PE 头验证 service.exe/naming.exe 子系统 = GUI(2)
3. `flutter build windows --release`（runner main.cpp 的控制台修复一并编入）
4. 启动验证：双击运行，确认**无终端窗口弹出**（上次修复的最终实物验证）

## Phase 3: 手机端部署（~15分钟）
- 若 `flutter/android/app/src/main/jniLibs/` 有预编译 libluoda.so：`flutter build apk --release` + `adb install -r`
- 否则复用手机上已装版本（本次改动核心在 PC 端 UI；chat_model 修改为双向生效，如 APK 无法重建则记录该限制，以 CI 产出的新 APK 为最终验证）

## Phase 4: 自动化测试套件 — 测试第 2-3 轮（~30分钟）
1. `flutter test`（全部 53 个测试文件）
2. `cargo test --release --features flutter`（lib 单元测试 + viewer_invite_policy/viewer_p2p/viewer_session 集成测试，与 CI 的验证步骤完全一致）
3. 重复跑一次 flutter test 检测 flaky 用例

## Phase 5: 真机 E2E 测试 — 测试第 4-8 轮（核心，每轮 20-40分钟）
每轮记录到测试日志（TEST_LOG_2026-08-22.md），每轮采样进程内存/线程数/CPU（tasklist + typeperf）：

- **第 4 轮 · 启动完整性**：无终端弹窗、主窗口/托盘/CM/服务 4 进程齐全、PE 子系统校验、启动耗时
- **第 5 轮 · 会话名称一致性**（上次修复验证）：消息列表名称 vs 顶部标题栏名称，含联系人和会议群两种场景，多设备合并行
- **第 6 轮 · 图片预览独立窗口**（上次修复验证）：真实 OS 窗口、可拖拽移动、最小化/最大化/关闭按钮全可用、多开不挂起（重点验证 initEnv 跳过是否根治了上份报告的子窗口引擎挂起）
- **第 7 轮 · PC↔手机消息 E2E**（上份报告 0 验证项）：文字/图片/文件双向收发（adb input 模拟手机端操作 + PowerShell 截图/仓库 OCR 脚本断言 PC 端状态 + RuntimeLogger 日志核对）、送达回执、两端名称显示
- **第 8 轮 · 资源与稳定性**：30 分钟空闲内存增长曲线、空闲 CPU、线程数变化、CM 管道错误计数（上份报告每 10 秒断开一次 os error 232、累计 1520 次——本次重点复测）
- **第 9-10 轮 · 回归与泄漏检查**：重复第 4+6+7 轮关键路径 + 连续 10 次启动/退出循环，确认无句柄/内存泄漏、无可复现崩溃

## Phase 6: 问题修复与优化（时间视发现而定）
已知目标（来自上份报告 + 本轮复测）：
1. **CM 管道每 10 秒断开**（os error 232）→ 检查 `src/ui_cm_interface.rs` 重连逻辑/超时配置——最优先
2. **线程数 205 偏高** → 定位 webview/蓝牙/音频插件线程池堆积来源
3. **内存 400MB 基线** → 对比 Flutter 标准基线，找增长点
4. 改动文件相关的 analyzer warning 清理
5. UPnP 10060（环境相关，低优先级，记录即可）
每个修复 → 重建 → 针对性复测（如影响核心路径则追加测试轮次）

## Phase 7: 提交与推送（~10分钟）
1. 整理未跟踪文件：保留 TEST_REPORT/TEST_LOG/有用的新组件，删除调试残留，合并 proguard 重复
2. git add + commit（中文提交信息，说明测试结论）
3. push 到 `origin/3.1.1`——自动触发 build-exe/build-msi/build-client-exe/build-apk 全部工作流

## Phase 8: CI 监控与修复闭环（1-3小时，轮询）
1. `gh run list/watch`（或 GitHub API）监控 4 条工作流
2. 任一失败：立即拉取日志定位 → 本地修复验证 → push 修复 → 循环直到全绿
3. 收集最终产物（LDesk-3.1.1-Setup-x64.exe / portable / MSI / APK），确认 Release 发布状态，输出最终验证报告

## 交付物
- 10 轮测试日志（含资源采样数据）
- 修复清单与优化报告
- CI 全绿的最终构建产物

## 风险与对策
- 本地 Rust 构建环境（opus/vpx 头文件）可能缺失 → Phase 0 先反查 8/22 成功构建时的环境；最坏情况以 CI 构建作为 Rust 编译验证
- Android APK 本地重建可能缺 NDK 工具链 → 复用已装版本 + 以 CI APK 为最终验证
- E2E 消息测试自动化程度有限 → adb 模拟输入 + 截图 OCR + 日志三角验证；无法自动化的项明确标注"需人工复核"
