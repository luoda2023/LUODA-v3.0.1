# 点聊 多方视频会议 + 会议纪要 融合设计（v2 — P2P 架构）

> 依据用户 2026-09-02 最终确认：
>  1. 效果图：大屏(桌面/电视)分格显示所有参会者；手机端自己/主讲全屏，
>     底部可横向滑动查看其它在线参会者的视频。
>  2. 网络架构不变：保持点聊现有连接方式，**尽量 P2P 直连，
>     尽量少占中继服务器资源**（中继仅 NAT 打洞失败时兜底）。
>  3. 会议纪要融入点聊聊天。
> 状态：v2 设计（取代 v1 的 Jitsi SFU 主线），待评审后实施。

## 0. 为什么不用 Jitsi SFU（替代 v1 决策）

| | Jitsi SFU（v1 路线 B） | 点聊 P2P 网状/星型（v2） |
|---|---|---|
| 媒体路径 | 全部经服务器转发 | 端到端直连；中继仅兜底 |
| 服务器成本 | 8C16G 只够 2~3 场 10 人会 | 几乎为零，信令走现有点聊中继 |
| 与现有代码契合 | 需另建一套 WebRTC/JWT/房间体系 | 复用点聊 connect()/camera/voice 通道 |
| 符合"尽量P2P、少占中继" | ✗ 违背 | ✓ 完全符合 |
| 网络穿透 | 自带 coturn | 已有 ID 中继 + 直连打洞 |

结论：按用户约束，媒体层必须走点聊自有 P2P 通道，v2 取代 v1。

## 3. P2P 媒体拓扑（网络架构不变）

```
                    ┌──────────────┐
  手机B 摄像头 ─────▶│  大屏/PC 端   │◀───── 手机C 摄像头
  手机A 摄像头 ─────▶│ (主持人/聚合) │◀───── 手机D 摄像头
                    └──────────────┘
  手机B ◀────(需要时)──── 大屏转发 ◀──── 手机C   (A看不到B时)
  中继 dotchat.dicad.cn:23116 —— 只用于 ID 注册 + NAT 打洞失败兜底
```
- **小会（≤4 端）**：全 P2P 网状，各端互相直连，服务器 0 媒体
- **大会（>4 端）**：星型——各手机只推 1 路上行给"主持大屏端"，由大屏端聚合/转发（大屏端多为 PC 带宽强）
- 复用 Rust 侧既有 Client 类型：新增 `conference` 类型（或组合 camera+audio 多路），经现有 rendezvous 信令交换 SDP/候选

## 6. 风险与对策
| 风险 | 对策 |
|---|---|
| P2P 网状带宽：N 人=每人 N-1 路上行 | 小会直连、大会星型；自动降码率 |
| 手机后台杀进程 | 前台服务 + 通知（复用 MainService 模式） |
| 不同网段打洞失败 | 现有点聊中继兜底（仅转发失败者） |
| 多方画面清晰度 | H.264 硬编 + 码率自适应 + 网格按需订阅 |
| 纪要转写算力 | 复用已实现 AI 纪要；后续可加录音转写 |

## 3.1 组织者(主持人)角色模型 — 用户 2026-09-02 确认

- **某一方(发起会议的设备,通常是大屏/PC)承担"组织会议"角色**,
  其它端只把自己的摄像头/麦克风 1 路上行给它 —— 无需全网状。
- 组织者职责:收 N 路媒体 → 聚合/布局(大屏网格) → 按需分发给需要看的端;
  维护成员表、举手、邀请码;必要时可**移交主持人**给另一强端。
- 各自带宽自适应:上行 720p/30 不够就降 360p/480p,网络好再升回;
  组织者下行强(PC),弱端只维持 1 路上行 —— 中继服务器零媒体占用。
- 纯 P2P 兜底:两手机在 NAT 后打洞失败时,才由点聊 ID 中继转发该路的信令/媒体(仅个例)。
